Is there a happens-before edge between T12 and T15?

1. Direct: NO. No lock, no volatile, no atomic between the two threads.

2. Indirect via HUB RX thread (9090):
   - HUB RX thread (9090) calls conn_->readPacket() (JNI)
   - JNI call creates a native↔JVM synchronization point
   - But the HUB RX thread does NOT read or write activeTransport
   - The HUB RX thread and the CLI bridge worker thread (10602) have NO
     direct synchronization

3. Indirect via AdbEngine.localhostConnected() (JNI):
   - AdbBackend.ensureConnected() calls AdbEngine.localhostConnected()
   - This acquires g_local_mutex (native mutex)
   - The probeLocalhost() also acquired g_local_mutex
   - BUT: g_local_mutex protects g_local, NOT activeTransport
   - The mutex does NOT create a happens-before for the Kotlin var activeTransport

4. Indirect via AdbRuntime.state:
   - ensureReady() reads state (same thread as activeTransport read)
   - state was written by the same IO thread as activeTransport
   - If state is visible (READY), activeTransport SHOULD also be visible
   - BUT: no formal guarantee (both are plain vars)

5. In practice:
   - 5.2 seconds is a LONG time for cache coherence
   - On ARM64 (Cortex-A76+), cache coherence is hardware-managed
   - The read SHOULD see the updated value after 5 seconds
   - But the JVM may have cached the value in a register or CPU cache

=== ALTERNATIVE EXPLANATION ===

If activeTransport was correctly read as LOCAL, then localhostConnected()
must have returned false. This would mean isOnline() returned false at T16,
which contradicts the HUB08 EAGAIN loop (which implies the socket is still
open and the transport is "alive").

However, there is a subtle possibility: the HUB RX thread (9090) and the
CLI bridge worker thread (10602) may see different states of the native
transport. The HUB RX thread is in a JNI read loop, while the CLI bridge
worker thread makes a fresh JNI call to localhostConnected(). If the native
transport state changed between the HUB's last read and the CLI bridge's
localhostConnected() call, the two threads could see different results.
