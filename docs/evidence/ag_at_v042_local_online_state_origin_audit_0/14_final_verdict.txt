=== INFERENCE ===

1. adbd's "already offline" indicates the host session is in a state where
   it does not send data to the client. This is NOT a key trust issue
   (key is authorized) and NOT a TCP issue (connection is ESTABLISHED).

2. The difference between AT (works) and AG (fails) is in the adbd SESSION
   STATE, not the client. AT's session (host-27) sends data; AG's session
   (host-23) does not.

3. The AG command execution path (Wireless instead of Local) is a
   CONSEQUENCE of the adbd session being unresponsive, not the cause.
   The transport observer or onOperationResult switches activeTransport
   to WIRELESS, causing the command to fail on a non-existent Wireless
   connection.

4. The ROOT CAUSE is in the adbd session management: adbd creates a host
   session for AG's connection but does not send data. This is likely due
   to the "already offline" state, which may be caused by:
   - A previous connection on the same host-N number
   - adbd's session lifecycle management
   - A race condition in adbd's TCP connection handling

=== UNKNOWN ===

1. WHY adbd says "already offline" for AG but not for AT (or for AT in
   the clean state test). The adbd log shows "already offline" for BOTH
   AT and AG in the clean state test, but AT still works.

2. The EXACT mechanism by which adbd decides to send data to one session
   but not another, given identical keys and identical handshake sequences.

3. Whether the "already offline" state is a red herring (always logged)
   or an actual indicator of session state.

=== MINIMUM_FIX_DIRECTION ===

The fix should address the FIRST divergence point:
  adbd session for AG's connection is unresponsive.

Possible directions (NOT implemented, forensics only):
  a) Investigate adbd's "already offline" log: what triggers it?
     Is it a bug in adbd's TCP session management?

  c) Ensure the AG command execution path uses the LOCAL transport
     (executeShellLocalhost) instead of falling back to WIRELESS when
     the LOCAL transport is unresponsive.
